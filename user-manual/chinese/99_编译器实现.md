

## zno 文件格式

编译器在编译一个库组件的时候，除了生成对应的 `.o` 二进制文件之外，还需要生成类似 C 语言的 “头文件”，包含所有的公开接口的签名，让下游库使用。
zinc 语言生成的 “头文件” 以 `.zno` 作为文件扩展名， 取 “氧化锌” 之意。

`.zno` 文件内容，包含所有的公开的函数签名、类型定义、全局变量声明、impl声明等。还包含所有可以跨组件内联的函数的函数体。

`.zno` 文件格式可以用纯文本形式、或者任意一种自定义二进制格式，原理上都没问题。但是为了加快编译速度，最终选择采用了 sqlite 文件来实现。下面解释一下这么做的理由。

考虑这种场景，在一个大项目中包含很多很复杂的组件。组件 a 依赖了组件 b，b 又依赖了其它组件 c、d、e 等。
如果使用简单的文本文件格式，那么编译组件 a 的时候，就不仅需要把组件 b 的 zno 文件全部读进来，而且需要把组件 b 所依赖的所有其它组件的 zno 文件全部读进来，然后做语法语义分析。
C/C++编译器的 `#include` 功能就是这么实现的。
但对于 Zinc 的模块系统来说，不适合直接照抄 C/C++ 的设计。因为 C/C++ 是以文件为编译单元，Zinc是以 component 为编译单元，编译单元的体量是更大的。
做个类比，相当于把一个 C/C++ 较大的模块的所有直接或者间接使用的头文件合并成了一个巨大文件，其它文件任何时候都 include 这个巨大的头文件，而不是手动拆分成若干小型头文件。
而且我们还要考虑跨组件内联的需求，有些函数的函数体也是需要在这个头文件中做记录的。
对于大型项目而言，过大的头文件对编译时间是一个很大的浪费，因为这一大堆的 zno 里面大部分内容在编译组件 a 的时候用不到。
因此，我们能不能考虑一下让 zno 支持按需读取功能，在编译 a 的时候需要什么读什么？按每个 “声明” 的粒度，把 zno 文件切分开来，而不是以文件为粒度整体读入。
比如组件 a 只是简单用了组件 b 中的一个函数 `fn f();`，，那我就知道 b 里面的其它函数声明、类型定义等等，都跟组件 a 没有关系，b 的依赖项也跟 a 没有关系。
我就可以从 `b.zno` 文件中把这样一个函数签名单独挑出来，做语法语义分析，其它内容不用管。不论 b 的 zno 文件有多么庞大，它的依赖树有多么复杂，这跟编译 a 都没有什么关系。

为了达到上述目标，我就需要把整个头文件按不同的声明切分成多个部分，并建立索引方便查询，而这正是 sqlite 可以帮忙做好的事情。

使用 sqlite 格式的好处有：
1. sqlite是最方便支持 “按需读取功能” 的格式，如果我们设计自己的文件格式，要达到同样的效果，最终很可能是做了一个更简化、更难用、bug更多的sqlite格式文件。
2. 读写速度快，文件大小也合适。有现成的辅助工具，成熟稳定，方便调试。后续修改 schema 扩展功能也很方便。
3. 目前阶段为了实现简单，是直接在sqlite中保存的序列化出来的源代码，后续也可以修改为保存中间代码 IR，进一步提升编译速度。而这并不需要修改总体设计。

zno 文件并不需要关注人类可读性，因为这个文件是给编译器用的，不是给人阅读的。
给人阅读的功能应该包含在文档生成工具中，我们应该提供一个 doc generator 工具，生成美观的 HTML 格式的文档，带有优美的排版、代码高亮、超链接、搜索功能等，方便人类阅读。

## 自举 bootstrapping

zinc 编译器第一个版本是 C++ 实现的，后来把前端又用 zinc 重新实现了一遍（当然不包括后端用的 LLVM 框架）。这么做有几个目的：

1. 编程界有一句名言 “Eating your own dog food”。设计者首先要热爱自己设计出来的产品，长期重度使用自己的产品，这样可以有效形成 Plan-Do-Check-Act 循环，有助于尽早发现问题加以改进。我非常希望我的日常工作的编程语言就是 zinc，直接用它来编写自己的编译器，可以最快积累第一手的使用体验，快速发现和改进问题。第一个版本不用 Rust 实现也跟这个有关，因为 Rust 的思维习惯、设计模式都跟 zinc 大不一样。比如说 Rust 实现的编译器内部的很多数据结构，要改用索引代替指针，这种思维方式跟其它语言区别很大。既然早就确定了后面会用 zinc 重写，那不如用 C++ 写第一个版本，那么第二个版本就可以在不改变主体架构的情况下无缝迁移。
2. 方便开源之后接受其他开发者的贡献。如果编译器本身是用 C++ 实现的，那么面对互不认识的开源贡献者的PR，我个人感觉很难做好代码审阅，维护代码的质量。而审阅安全的编程语言实现的功能，则简单得多。
3. 践行 compiler as a service 的理念。众所周知，一门编程语言，不止是实现一个编译器，它还需要一整套的生态系统才能真正有用。这个生态系统中的工具链部分，包括了集成开发环境 IDE 支持、代码自动格式化工具、包管理工具、文档生成工具、自定义lint告警、代码质量分析 等等一系列的工具。而这些工具有很多部分都需要和编译器共享相同的逻辑。所以，如果我们能让编译器本身的各个部分，都是比较方便调用的 library，具有安全、易用的 API，那么构建周边工具就事半功倍。反之，如果编译器是一个黑盒子，它的组件无法被轻松复用，那么构建周边工具就有大量的重复性工作要做，事倍功半。用 C++ 作为编译器本身各个子组件对外的 API 接口，不够安全、易用。
4. 为后续的元编程(宏、自定义lint等)功能打下基础。所谓元编程，从实现层面来讲，其实就是编译器插件功能。需要编译器动态加载一些模块，在编译过程中执行这些插件的功能。我们当然希望宏定义本身是用 zinc 实现的。而且 zinc 恰好是比较适合被编译成动态链接库的语言，编译出来的库的API还可以支持泛型、trait等高级功能。编译器作为调用方，如果也是zinc实现的，那么这个插件机制就非常干净简洁。反之如果用C++动态加载zinc的动态链接库，虽然可以做，但明显是节外生枝的麻烦事。

## 编译器结构简介

编译器分这几个组件：
* zinc_cli 可执行程序，依赖下面几个组件。它内部主要包含命令行处理功能。
    * options
    * session
* zinc_frontend 编译器前端, 负责语法语义检查，它包含多个子模块，其中两个最主要的模块是：
    * zinc_syntax  主要输入是源码，输出是 SyntaxTree 这个数据结构。包含语法报错功能。lexer 也包含在这个组件里面。
    * zinc_semantic  主要输入是 SyntaxTree 这个数据结构，输出是 SemanticModel 这个数据结构。包含语义报错功能。
        * hir
        * mir
* zinc_backend 编译器后端，负责性能优化和代码生成，它包含多个子模块，其中两个最主要的模块是：
    * optimization 性能优化，输入是 SemanticModel 这个数据结构，对其进行修改、变换
    * llvm_ir_gen 主要输入是 SemanticModel 这个数据结构，输出是 LLVM IR。它里面也包含一些性能优化。


它们都依赖 zinc_std，这个是 zinc 的标准库。

## 不支持基于参数类型的函数重载

主要目的是为了更好地支持基于动态链接库发布组件。

核心场景是：当一个组件用动态链接库对外发布的时候，我们期望可以在后续更新库的版本的时候，下游用户不需要重新编译代码，直接就可以链接使用。

现在假设我们支持基于参数类型的函数重载，考虑这种情况：
lib_v1 中有一个函数，签名为 `fn f(arg: *Base);`，在 lib_v2 版本中我们想新增一个重载版本 `fn f(arg: *Sub);`，其中 `Sub` 是继承自 `Base` 的 trait。
下游用户如果不重新编译代码，和 lib_v2 一起使用的时候，代码依然能执行，但它永远都是调用的 `Base` 版本。这个新增重载根本不会生效。

当我们说 “不支持基于参数类型的函数重载”，实际意思是，“不支持在编译期基于参数类型做函数版本解析”，我们强制要求用户在运行期做函数版本解析。

还是上面那个场景，如果用户需要在 lib_v2 中对 `*Sub` 类型的参数做额外的处理，用户需要修改原函数的函数体，而不是新增一个重载版本的函数签名:
```
fn f(arg: *Base) {
    if (arg is s:*Sub) {
        // 通过模式匹配判断, 如果 arg 是 *Sub 类型, 则执行特殊逻辑
    } else {

    }
}
```
新版本 lib_v2 的动态链接库发布后，可执行程序不需要重新编译，这个应用的行为就自动更新了。

这么做当然会牺牲执行效率。但是为了实现动态链接库的无感更新，这个运行时代价是必须要付出的。编译期做重载解析，是无法获得这种动态性的。

这种设计没有表达能力问题，只有执行性能问题。而执行性能是有机会通过各种优化措施弥补一部分的。特别是当用户不需要 “发布ABI稳定的动态链接库” 这个需求的时候，可以通过编译选项告诉编译器，开启更激进的优化。

## 没有异常(exception)、栈回溯(unwind)

zinc 语言提供了 `panic` 关键字，可以类比为其它语言中的 `throw` 关键字。但是它跟其它语言的 `throw` 或者 rust 中的 `panic!` 不是一回事。

Rust 的 panic 有两种行为模式，分别为 `abort` 和 `unwind`，可以通过 `rustc` 的下面这个编译选项指定。
```
-C    panic=val -- panic strategy to compile crate with
```
* rust 中的 `panic` 在 `abort` 策略下，会直接终止进程，`catch_unwind` 函数不起作用。等价于调用 libc 的 `abort` 函数。
* rust 中的 `panic` 在 `unwind` 策略下，会执行栈回溯(unwind)，并调用每层函数中局部变量的析构函数，包括ARC指针的引用计数自动减一等操作，而且它能被 `catch_unwind` 捕获，终止栈回溯的过程。这个过程与其它语言的 exception 是类似的。

zinc 中的 `panic` 就是简单的打印函数调用栈，然后 abort。它没有 unwind 的过程，是无法被捕获的，仅相当于 rust 中的 `panic` 在 `abort` 策略下的行为。zinc 不支持 `unwind` 这种行为。

这个设计是受到 nikomatsakis 的这篇 [博客](https://smallcultfollowing.com/babysteps/blog/2024/05/02/unwind-considered-harmful/) 的启发，而选择这么做的。理由有以下几点：

1. unwind 会增加编译器、标准库的实现难度
    1. unwind 会增加代码体积。因为每个函数调用，都有可能发生栈回溯，编译器需要记录每个可能发生栈回溯的地方要调用哪些局部变量的析构函数。
    2. unwind 会减少优化机会。代码的控制流图会变得复杂，很多地方会多一条可能发生unwind的控制流，这会影响编译器的静态分析。
    3. unwind 会要求标准库在实现的时候考虑异常安全(exception safety)这个问题。
2. unwind 会增加用户的学习和使用成本
    1. zinc 作为一门后发语言，很难建立独立的生态。在大部分应用中，大家很可能只是用 zinc 开发其中的某一个模块，这意味着互操作很重要。zinc 如果引入 unwind 机制，那么它和已有的 C++ 的 exception、Rust 的 panic 是什么关系，是否可以互相捕获？如果我们希望 zinc 编写的底层模块可以被上层语言 Go/C#/Java/Javascript/Python 等调用，这些高级语言是否可以捕获 zinc 抛出的 panic？ 这个机制究竟对用户来说是方便，还是添乱？
    2. 语言中引入 unwind 机制，就要求所有第三方库，在设计的时候都要考虑异常安全(exception safety)这个问题。特别是在涉及unsafe以及互操作的时候，这个事情很难。zinc 的定位是强调简单易用，要求普通开发者也考虑异常安全设计，要求是不是高了点？
    3. 有哪些错误处理场景，是用 `Option` `Result` 不方便表达，一定要用可捕获的 unwind 来做的？如果我们实现这个特性，有哪些场景能受益，这些场景是否足够有说服力？

本人觉得，zinc 的生态应该建设成这个样子：所有 “可恢复的错误” 一律返回 `Option/Result` 类型，这类错误意味着本进程在碰到这类错误的时候是有处理手段的。所有 “不可恢复的错误” 一律用 `panic`，这类错误的意思是，当前应用程序在运行阶段对这类错误是没有任何处理手段的，这是代码中的 bug，唯一的解决办法是回去修改代码重新编译程序，重新执行。

如果有其他人不同意此决策，需要编写一份完整的设计提案开展讨论，内容应该对上述疑问做出充分解答。
