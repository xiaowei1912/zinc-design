
# 并行并发

## 线程安全

Rust 有一个无与伦比的优点：它天然保证了程序的线程安全。在常用编程语言中，它是独一无二的。Zinc 语言也希望能保留线程安全这个特点。

### Send/Sync trait

我们把所有可以安全地跨线程传递的类型，做一个统一标记，叫做 `Send trait`。

首先我们回顾一下，[值语义和引用语义](https://isocpp.org/wiki/faq/value-vs-ref-semantics#val-vs-ref-semantics) 的含义。

可以看出来，值语义的类型，天然满足 `Send trait` 的要求。举例如下：
1. 基础类型 Bool, Char, Int 等，符合值语义，因此肯定满足 `Send trait`。
2. 组合类型，如 tuple/struct/enum 等，如果所有的成员都是满足 `Send` 的，那么它也一定是值语义的，所以这种类型也是满足 `Send trait` 的。
3. 指针类型不符合值语义，一般情况下 `*T` 不满足 `Send` trait。但是也需要根据具体情况分析。指针类型、或者内部包含指针成员的类型，在以下两种情况也满足 `Send`：
    1. 通过 copy-on-write 机制，实现了值语义，这些也满足 `Send` trait。比如 `String` 类型，虽然它内部包含指针成员，但是因为它的实现通过 copy-on-write 保证了“值语义”，所以这种类型也是满足 `Send trait` 的。对于 `Vec<T>` 这种类型，虽然它也实现了 copy-on-write，但因为它带有泛型，所以它是否满足 `Send` 是带有前提条件的。当且仅当 `T: Send` 的时候，`Vec<T> : Send`。
    2. 通过线程同步机制，保证指针指向的内容是线程安全的，这些也满足 `Send` trait。比如 `*AtomicInt32` 类型，虽然可能出现两个线程中的不同指针都指向同一个 `AtomicInt32`，但因为 `AtomicInt32` 是做了线程同步的，所以 `*AtomicInt32` 类型就是满足 `Send` trait 的。

因此，我们再引入另外一个 `Sync trait`，代表一个类型本身具备线程同步能力。那么，我们可以说，对于 `*T` 类型，当且仅当 `T` 满足 `Sync` 的时候，`*T` 满足 `Send`。
对于借用指针，同理。当且仅当 `T: Sync`，则 `&T : Send` 且 `&mut T : Send`。

满足 `Sync trait` 的类型举例如下：
1. `Atomic` 系列类型
2. `Mutex<T>` `RwLock<T>` 等类型。注意：因为这些类型本身是带泛型的，它们是否满足 `Sync` 是有前提条件的。当且仅当 `T: Send` 的时候，`Mutex<T> : Sync`。

有了这两个 trait 之后，我们还需要做两件事，就可以保证线程安全：
1. 在标准库中，给所有的基础类型，以及标准库定义的类型，都打上 `Send` 和 `Sync` 的标记。
2. 在需要在不同线程之间传递数据的 API 上，增加约束，限制跨线程传递的类型，必须满足 `Send` 条件。

用户自定义类型，一般情况不需要手动标记 `Send` `Sync`，靠编译器自己推理出来的结果即可。
如果这个类型的实现使用了 unsafe，此时需要程序员自己分析该类型是否满足  `Send` `Sync`，通过 unsafe impl 显式指定。

### 无数据竞争

当编译器和标准库中准备好了上述的 `Send` `Sync` 类型之后，我们就可以通过编译检查保证业务代码中 “无数据竞争”。
如果出现了数据竞争的可能性，编译器会自动报错。

示例如下：

```
// 假设 send 函数要做的事情是把 data 发送到另外一个线程中使用，那么它就需要限制 data 的类型满足 Send 约束
fn send<T>(data: T) where T: Send { }

fn main() {
    send(1_i);
    send(String::new());
    send((type Vec<Int>)::new());
    send(box 1_u); // Error. 编译报错 *UInt 不满足 Send 约束
}
```

### 全局变量

全局变量，天然可以被不同的线程访问，因此也需要对它做限制，来保证线程安全。
1. 全局变量的定义可以用 `static` 或者 `unsafe static` 关键字修饰。 `unsafe` 修饰的全局变量，只能在 unsafe 区读写。只有 `static` 定义的只读全局变量，是安全的。
2. 没有 `unsafe` 修饰的全局变量的类型必须满足 `Send trait` 的要求。

**注意**：跟 Rust 的规则不同，Zinc 要求全局变量满足的是 `Send` 约束，而不是 `Sync` 约束。

因为 Zinc 的 `Sync trait` 和 Rust 的 `Sync trait` 语义是不同的。在 Rust 中满足 `Sync` 的很多类型，在 Zinc 中是不满足 `Sync` 的。
以基础类型 `Int` 为例，在 Rust 中是满足 `Sync` 的；但在 Zinc 中，`Int` 不可满足 `Sync`。
通过反证法可得，如果我们规定 `Int` 满足 `Sync`，那么意味着 `*Int` 这种指针满足 `Send`，那么它就可以跨线程传递，然后我们就可以看到两个线程都获得了指向同一个 `Int` 的指针，且没有做线程同步，这是错误的。

* Zinc 中的 `Sync` 代表的是内部有额外线程同步机制的类型。满足 `Sync` 约束的类型要比 Rust 中要少得多。 
* Zinc 中的 `Send` 代表可以安全地跨线程传递的类型。主要包含四种情况：

    1. 经典的值语义类型，内部不包含指针，它在跨线程传递的时候是拷贝一个副本，因此肯定是安全的
    2. 类型中包含指针，指针指向的数据是只读的。共享数据是只读的，因此是安全的。
       比如 `Str` 类型，它的对外 API 不提供任何修改能力，这样可以保证 `Str` 是满足 `Send` 的。
    3. 类型中包含指针，指针指向的数据满足 copy-on-write。如果有线程尝试修改共享数据，它会把共享数据拷贝一份再修改，只要数据处于共享状态就肯定不会被修改，修改的永远是自己拷贝出来的副本，因此是安全的。
       比如 `Vec<Int>` 类型，所有的具备修改能力的成员函数，都会判断引用计数，如果不是独占的，就先把数据拷贝一份再修改
    4. 类型中包含指针，指针指向的数据可在线程同步前提下修改。它跨线程传递之后，会有多个线程持有指向同一份数据的指针，但所有的对共享数据的读写都有线程同步，因此是安全的
       比如 `*AtomicInt` `*Mutex<String>` 类型


虽然 Zinc 和 Rust 设计的 `Send` 和 `Sync` 的一些细节有区别，但都做到了保证线程安全。


<div style="border: 1px solid black; padding: 10px; background: #F0F0F0">

从上面的设计可以看出，像 `Vec<Int>` 这一类的类型，是满足 `Send` 约束的。我们可以安全地把这种类型跨线程传递。

1. 如果我们把 `Vec<Int>` 传递到不同线程，且每个线程都只是对它只读，那么只会发生浅拷贝，执行效率很高。
2. 如果我们把 `Vec<Int>` 传递到不同线程，且存在某个线程对它做修改，那么在这个线程发生修改的时候，触发深拷贝，此时有较大性能开销，但是不会有线程安全问题。
3. 如果我们希望把 `Vec<Int>` 跨线程传递，能被修改，且不发生深拷贝。那么需要程序员自己保证它不会同时存在多个浅拷贝实例。此事可以通过 move 表达式来达到目的。
把一个 `Vec<Int>` 在不同线程转移所有权，即可实现高效跨线程修改的目的。但编译器不在类型层面跟踪所有权，只在控制流层面跟踪，减少对用户的影响。
4. 如果我们希望拿到引用语义的 `Vec<Int>` 只需要把它 box 一下即可，得到的 `*Vec<Int>` 就是引用语义的类型。不同的指针可以对同一个 `Vec<Int>` 做修改，共享同一块数据。
因为 `Vec<Int>` 不满足 `Sync`，所以 `*Vec<Int>` 不满足 `Send`。此时编译器可以帮我们检查，所有这些指针都是在同一个线程内部的，非 `Send` 类型不可能跨越线程边界。
所以引用语义的 `*Vec<Int>` 类型也不会有线程安全问题。而且这个Arc指针的引用计数操作可以被优化为 non-atomic 加减操作。

由上可以看出，copy-on-write 优化对于 `Vec<T>` 这种类型非常重要。

我们假设 Zinc 语言不是选择 ARC 作为内存管理的基础机制，而是选择了 GC，让 `box` 表达式返回的是 GC trace-able 的指针。
那么像 `Vec<T>` 这种容器类型，它的内部实现只能使用 GC 指针，就不能做到 “值语义” 类型。它就只能是 non-Send 的。而且 move 表达式也没有了意义。
这样的话，在多线程场景，能够满足 `Send` 约束的类型寥寥无几，为了保证线程安全，需要做深拷贝的场景就更多，反而带来巨大的额外性能开销代价。
因此 ARC 内存管理和 Zinc 的线程安全目标是最契合的。

而正是因为 Zinc 也做到了线程安全，我们就能在编译时保证某些 ARC 指针，是一定不可能穿越线程边界的，它自己以及它的复制品都只能在同一个线程内使用。
利用这个信息，编译器可以将它们的引用计数的加减操作，优化为非原子操作，进一步提高性能。这个优化只跟类型相关，跟控制流无关。

因此，线程安全与 ARC 内存管理，是珠联璧合、相得益彰。

## 线程

Zinc 标准库提供的线程相关 API 就是对操作系统的线程功能的简单封装。创建线程用下面这个函数：

```
// mod std::thread
pub fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: Send + 'static + Fn()->T,
    T: Send + 'static,
```

`JoinHandle` 可以调用 `join()` 函数等待线程结束。还可以调用 `thread()` 函数获取 `&Thread` 类型的变量。

示例如下：

```Rust
use std::thread::spawn;
fn main() {
    let h = spawn.{
        println("thread 2");
    };
    println("thread 1");
    h.join().get_or_panic();
}
```

### ThreadLocal

`ThreadLocal` 类型用于表达 “线程局部” 变量。每个线程都独立维护各自的副本。

使用方式如下：

```
use std::thread::spawn;

fn main() {
    static G: ThreadLocal<Int64> = ThreadLocal::new(0);

    let h = spawn.{
        *G += 1;
    };
    h.join().get_or_panic();
    println(*G);
}
```

## 锁

锁包括 `Mutex<T>` `RwLock<T>`。

Rust 的锁的 API 设计有一个很好的优点：它把锁和被保护数据合并为一个类型，从而避免了锁和被保护数据不匹配的情况，也不可能出现访问数据忘记上锁的场景。

但它有几个小问题：
1. poison 设计
2. 可能在 safe 代码中允许 MutexGuard 泄漏，出现无法解锁的场景
3. 在异步代码中，如果在上锁的时候发生await，则很容易触发死锁

Zinc 对这套 API 做了一点小小的修改：
1. 取消 poison 状态管理，因为 Zinc 没有 catch unwind 的机制
2. 加锁和解锁改为回调函数式

```
fn synchronized(p: &Mutex<String>) {
    // 后续可以学习 swift 增加更多的语法糖，把 lambda 这个参数列表也省略掉
    p.lock.{ (data: &mut String) =>  
        data.push_str("tail");
    };
}
```

这么做的好处有：
1. 上锁的范围清晰，有大括号包围，比较显眼，适合人类阅读
2. 没有 MutexGuard，也就没有了泄漏风险，上锁行为必定对应解锁行为，避免了锁无法释放的风险
3. 在多层加锁的时候，可以确保加锁解锁一定满足先进后出原则。Rust 因为暴露了 MutexGuard，允许用户手动 drop MutexGuard，所以实际解锁的顺序有可能是非结构化的
4. 在回调函数中不可能使用 await 表达式，因为回调函数 API 类型不匹配，也就避免了在锁的过程中发生 await 这样的情况

当然它带来了一个缺点，就是再也不能像以前那样在上锁的过程中自然使用 `break` `continue` `return` 这些控制流语句，由编译器自动解锁。因为在回调函数中的控制流语句只影响 lambda 内部，如果需要处理外部的控制流，那么需要通过这个 lambda 的不同返回值在 lambda 外面做额外判断处理。当然话又说回来，这么写至少从可读性的角度来说，是非常清晰的。不能直接用控制流语句也未必就是坏事。

### 防拷贝设计

Rust 的锁的类型是设计成 move 语义的，但 Zinc 就没有 move 语义的类型。这就带来了一个新的风险，就是用户可能把一个 `Mutex<T>` 变量无意中复制一份，这就很容易产生 bug。

示例:
```
// 伪代码示例，该代码实际上无法编译通过
fn test(s: &Mutex<String>) {
    let str_copy = *s; // 某些情况可能这个拷贝很隐蔽，这就可能出 bug
    str_copy.lock.{ (s: &mut String) => println(s) };
}
```

在 Zinc 中，为了避免这种情况出现，引入了 `UnSized` trait。这个 trait 是一个 marker trait，没有成员函数。同时规定：
1. 允许在定义类型的时候，给自定义类型 `impl UnSized for MyType {}`
2. 所有的 `UnSized` 类型都不能直接用做 全局变量、常量、局部变量、成员变量。这种类型只能通过指针间接访问。
3. 不允许对指向 `UnSized` 的指针类型做解引用。

我们在标准库中把 `Mutex` 这种类型规定为 `UnSized` 就可以避免上面的 bug 出现。

```
struct S {
    value: Mutex<MyType>, // Error，Mutex 不能直接作为成员变量使用，建议用 *Mutex<MyType> 代替
}

fn f() { 
    let local = Mutex::new(MyType::new()); // Error，Mutex 不能直接作为局部变量使用，建议用 *Mutex<MyType> 代替
}

static GLOBAL_DATA: Mutex<MyType> = Mutex::new(MyType::new()); // Error，Mutex 不能直接作为全局变量使用，建议用 &'static Mutex<MyType> 代替

static GLOBAL_DATA: &'static Mutex<MyType> = &Mutex::new(MyType::new()); // OK
```

标准库中的 `swap` 等函数，也不能对 `UnSized` 类型操作。因此这个设计就可以避免上述的 "因为不小心而拷贝了整个 Mutex" 的错误。

标准库中的 `File` 等类型，也是类似的设计。用户永远只能使用 “指向 File 的指针类型”，而不能直接把 `File` 类型当做值类型使用。
