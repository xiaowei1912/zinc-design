# 内存管理

## ARC 指针

zinc 选择使用引用计数作为核心的内存管理策略。ARC代表 automatic reference counting。这个 automatic 的含义是，在对引用计数做加减操作的时候，编译器自动选择原子指令或者非原子指令。

在堆上分配的每一块内存，都会携带强引用和弱引用两个引用计数值。
当强引用计数降为0的时候：
* 如果弱引用的值不是0，那么这块内存的析构函数会调用，但是这块内存并不会释放。直到弱引用的值也降为0，再释放这块内存。
* 如果弱引用的值是0，则调用析构函数，并直接释放这块内存。

因为引用计数指针是最常用的指针类型，所以zinc把最简洁的指针语法，对应到 ARC 指针的语义上。 `*T` 类型就是代表的是指向 `T` 类型的 ARC 引用计数指针类型。

弱引用指针类型，使用 `*weak T` 来表达。指向 `T` 类型的弱引用指针，无法访问 `T` 类型的成员变量、成员函数，无法解引用。
弱引用指针必须通过 `std::ptr::upgrade` 函数，转换为强引用指针 `*T`，才能访问 `T` 的成员变量、成员函数。

把一个对象在堆上分配，使用 `box` 关键字。对于 `box <expr>` 表达式，如果 `<expr>` 的类型为 `T`，则 `box <expr>` 表达式的类型为 `*T`。
`box` 表达式如果发生内存分配失败，则直接 panic。
如果用户确实需要手动处理内存分配错误，可以自己调用 `std::alloc::try_box` 函数，通过判断返回值确定内存分配是否成功。
需要手动处理内存分配失败的场景，其实不大适合使用 zinc，毕竟整个标准库的实现，在 OOM 的时候都会直接 panic。仅仅在应用层做内存分配成功与否的判断是不够的。


示例如下：
```rust
let x: MyObj = MyObj::new();  // 如果 MyObj::new() 返回的是 MyObj 类型
let y: *MyObj = box MyObj::new(); // 那么 box MyObj::new() 返回的就是 *MyObj 类型

let z = y; // z 和 y 指向同一个 MyObj 类型的对象
```

指向静态大小类型（指 sized类型，暂时不讨论 unsized 类型）的 ARC 指针的内存布局长下面这样。每次动态内存分配，先 `malloc(sizeof(UInt) + sizeof(MyObj))` 然后让指针偏移到对象的首地址。
通过 ARC 指针访问成员变量，需要的偏移量就是这个成员相对于对象首地址的偏移量。
```
                ┌──────────────────────┐
                │ strong_count: UShort │
                │ weak_count: UShort   │
ptr: *MyObj  →  │──────────────────────│
                │ field1               │
                │ ......               │
                └──────────────────────┘
```

在出现环型引用的情况下，只要环上有一个是弱引用指针，那么这个环就能正常回收而不会发生泄漏。但什么时候用弱引用指针，需要程序员自己指定。

zinc 中没有 Rust 中的 ownership 概念，也没有跟 `Box<T>` 语义相似的类型，没有 move-only 的 “所有权类型”。

**注意**：没有 `*mut T` 类型。不论绑定的变量本身是不是 mut 的， `*T` 类型对它的成员永远有修改权限。

示例：

```rust
struct S { m: i32, n: i32 }
fn main() {
    let p1: *S = box { .m = 1, .n = 2 }:S ;
    p1.m += 10; // OK, 即使 p1 这个变量绑定不是 mut 修饰，它也有权修改成员变量

    p1 = box { .m = 10, .n = 20 }:S; // 错误, p1 这个变量绑定没有 mut 修饰，不能直接给它赋值
}
```

## 值语义和引用语义

[值语义和引用语义](https://isocpp.org/wiki/faq/value-vs-ref-semantics#val-vs-ref-semantics) 介绍：
1. 值语义意味着，拷贝的时候是把值复制了一份，新变量和旧变量互相之间没有任何关系。对其中任何一个的修改，在另外一个变量上面没有体现。
2. 引用语义意味着，拷贝的时候是对指针做拷贝，新变量和旧变量存在共享数据，对这部分共享数据的修改，会同时影响两个变量。

判断标准就用下面这段伪代码的逻辑：
```rust
let mut y: T = x;
modify(&mut y); // 对 y 做修改
print(x);
print(y);
// 如果对 y 的修改无论如何都影响不到 x，那么就可以说类型 T 是值语义的类型。否则，类型 T 是引用语义的类型。
```

zinc 鼓励用户在类型定义的时候，把它设计成 “值语义” 的类型。

因为一个定义为值语义的类型 `S`，那么它对应的 `*S` 类型就是引用语义，使用方可以很轻松的根据场景选择使用 `S` 或者 `*S` 类型。
而如果直接在类型定义时设计为 “引用语义” 类型，那就很难拿到它对应的 “值语义” 类型，对使用者来说是不方便的。

## 借用

为什么我们需要借用指针？

因为只有 ARC/WEAK 指针的话，表达能力是不足的。
`*T` 类型永远只能指向 “动态分配对象” 的头部。动态分配对象一定携带有引用计数值。因为它要操作引用计数值，它要保证引用计数值在它指向的地址的固定偏移处。
如果我们需要一个指针指向一个对象的中间，就不能用 `*T` 类型的指针。

如果这门语言中的所有安全的指针，都只能指向对象头部，那么对象的内存布局就没法紧凑。这种设计不利于值类型的发挥。

如果我们允许对对象的中间部分取地址，得到一个新指针，如下图所示：
```
                ┌───────────────────┐
                │ strong_count: u32 │
                │ weak_count: u32   │
ptr: *MyObj  →  │───────────────────│
                │ field1: i32       │
                │ field2: MyStruct  │ ← borrow_ptr: &MyStruct
                └───────────────────┘
```

那么这个 borrow_ptr 指针一定具备以下特点：
1. 它在运行时没有足够的信息，找到它指向的这个对象本身携带的引用计数
2. 它在运行时没有能力主动控制它指向的这个对象的生命周期

因此，借用指针的生命周期一定需要编译时静态检查，确保借用指针一定存活得比被借用对象要短，否则就会出现野指针问题。

所以，zinc也保留了 rust 的借用指针，以及生命周期参数。借用指针只能通过“取地址”操作来获得，编译器会在编译时跟踪借用指针的存活范围。
为了区分不同的可读写权限，借用指针被分成两种，可读写的 `&mut T` 类型和只读的 `&T` 类型。对应的运算符表达式，也是 `&mut <expr>` 和 `&<expr>`。

借用指针是对ARC指针表达能力的一个很好的补充：
1. ARC 指针只能指向堆上动态分配的对象；借用指针既可以指向堆上的对象，也可以指向栈上的对象。
2. ARC 指针只能指向堆上动态分配的对象的头部，不支持指针算数运算；借用指针可以指向对象的头部或者中间，可以通过对成员变量做借用操作实现指针偏移。
3. `*T` 类型在拷贝、传参的时候，总是需要增减引用计数，有额外性能开销。借用指针的赋值、传参、返回不需要操作引用计数值。合理使用借用指针，有助于减少冗余的增减引用计数运算。

zinc 和 rust 的借用指针的相同之处有：
* 都有生命周期检查。即编译器要在编译时做检查，保证借用指针本身，要活得比被借用对象更短。
* 都有读写权限检查。`&T`型借用只有读权限没有写权限，`&mut T`型借用有读写权限。

zinc 和 rust 的借用指针的不同之处有：
* 可变性规则不同。在zinc中，ARC指针类型 `*T`，不论这个变量绑定本身是不是可变的，永远可以通过这个变量获得 `&T` 和 `&mut T` 两种借用。
* zinc 没有 “所有权类型” 以及 “借用检查规则”。可读写借用不是独占的。语义规则宽松得多。


### 示例一：借用指向栈上地址
```rust
struct S { m: Int, n: Int }
fn main() {
  // 允许直接指向临时变量、字面量。此时编译器自动生成一个匿名局部变量，然后让借用指针指向它。
  let mut p2: &Int = &1;

  {
    let x1 = { .m = 1, .n = 2 }: S;
    let p1 = &mut x1; // 编译错误, 不能对只读变量 x1 获取可读写借用
    p2 = &x1.m; 
  }
  print(p2); // 编译错误，x1 活得比 p2 短

  let mut x2 = { .m = 3, .n = 3 }: S;
  let p3 = &mut x2; // 正确
  let p4 = &x2.n; // 正确
  p3.m += 1;    // 正确，p3 有写权限
  println(p4); // 正确，p3 和 p4 同时存在没有问题，p3 没有排他性
}
```

### 示例二：借用指向堆上地址

zinc代码示例如下：

```rust
fn main() {
  let mut b: *Int = box 1_i;

  let p1: &Int = &*b; // 允许，指向堆上的地址
  let p2: &mut Int = &mut *b; // 允许，指向堆上的地址

  // p1/p2 可以同时存在，mut型借用没有排他性
  println(f"$(p1)");
  *p2 += 1;
  println(f"$(p2)"); 

  b = box 10_i; // b 重新赋值

  // 读写 p1/p2/b 都没有问题，p1/p2 没有失效
  println(f"$(p1)");
  *p2 += 1;
  println(f"$(p2)"); 
  println(f"$(b)");
}
```
上述代码示例，如果用 Rust 来编写，把 `*Int` 改为 `Box<i32>` 的话，会发生编译错误。因为 Rust 的可变借用是独占的，无法与其它借用同时存在。但 zinc 可以编译通过，且没有内存安全问题。
原因是，在 zinc 中通过 ARC 指针对成员变量取借用的场景，编译器会一律生成一个额外的临时变量把 b 拷贝一遍，确保引用计数值 +1，然后再对成员变量取借用。这个临时变量会在当前 block 结束的时候释放，此时引用计数自动减 1。
因此后面对 b 的赋值，并不会导致原本指向的内存马上被释放，p1/p2 一直都是有效的，直到函数结束，原来那块内存才会释放。

下面是多层 ARC 指针的场景：
```rust
struct Obj { p: *Int } // zinc 没有 move 语义的指针类型，只能用 * 指针。

fn main() {
  let mut o: *Obj = box { .p = box 1_i }:Obj;
  let q: &mut Int = &mut *o.p; // 此时是对 p 这个指针临时复制一份, 而不是复制 o
  *q = 2; // q 有修改权限

  // 通过 ARC 指针创建借用指针
  let r: &mut Obj = &mut *o;
  r.p = box 10_i; // 允许，没有编译错误，也没有野指针。

  o = box { .p = box 100_i }:Obj; // 允许，没有编译错误，也没有野指针。

  println(*q); // q 还是指向原来的值，打印结果为 2
  println(*r.p); // r.p 指向新的值 100
}
```

总而言之，通过 Arc 指针创建一个新的借用指针的时候，zinc避免借用指针成为野指针的办法就是，保护性增加引用计数，延迟释放内存。
编译器只需要在一个函数内部做局部静态分析，就足以保证内存安全。

从执行性能的角度讨论：这个设计肯定会牺牲一部分执行性能，但应该不会影响太大。

1. 前面所讲的只是从语义的角度来解释代码的预期行为，并不是从优化的角度来描述具体的指令。

   从优化的角度来看，我们没必要在任何创建新的借用指针的时候，一律增加引用计数。只有当编译器无法在编译时保证借用指针指向的对象在这段区域内一定存活得时候，为了保险，会自动增加引用计数避免内存过早释放。
   很多场景下编译器有足够的信息，直接优化掉这些额外的引用计数增减操作。

2. 与Rust相比，有些堆上的动态分配的对象的释放时机被推迟了。

   从保证内存安全这个角度，其实标记清除式的GC也是类似的思路：只要还有指针指向这块内存，那么运行时就保证不会释放这块内存。
   区别只是标记清除式的GC可以处理循环引用，而ARC处理不了。
   注意到，在函数内部创建的借用指针肯定不能活得比本函数更长，所以如果一块内存，是因为存在借用指针导致它被延迟释放，那么这个借用指针所在的代码块结束之后，这块内存也就可以释放了，不会延迟太久。

3. 只要我们合理利用借用指针，相比于所有地方都使用 ARC 的设计，很多时候可以减少引用计数发生的频率。
   1. 一个借用指针，赋值、传参、返回使用的时候，是不需要对引用计数做修改的
   2. 通过一个借用指针，获取其成员的借用指针，只要成员变量不是 ARC 指针类型，是不需要对引用计数做修改的
   3. 即便是对 ARC 指针类型的成员变量取借用，也可以通过优化删掉一部分冗余的引用计数修改。这种优化取决于编译器有没有足够的信息知道，某个 ARC 指针指向的对象在某段生命周期内确定性没有被释放的风险。


从易用性的角度讨论：这个设计是对 Rust 的极大简化。**去掉了 borrow checker，没有了 &mut 型借用是独占式的这个限制**。做到了在类型层面，去掉了 move only 类型。


从内存布局的角度讨论：ARC和借用指针的配合，可以保证程序员对内存布局的控制力。
1. 所有的类型，它的内存布局都是确定性的，编译器不会隐式的插入什么隐藏的成员。
2. 只有我们明确使用 `box` 关键字在堆上分配内存的时候，才会在动态分配的内存的头部记录引用计数，此时有额外的引用计数内存开销。在栈上使用的局部变量，没有额外引用计数内存开销。
3. 任何类型作为成员使用的时候，都是直接平铺，没有额外引用计数内存开销。除非程序员指定成员变量是 ARC 类型，编译器不会不会隐式插入box操作和引用计数值。

## 更复杂一点的取借用操作

Zinc 的容器类型比如 `Vec<T>` 也支持对元素取借用操作。示例如下：

```rust
fn main() {
    let mut vec = (type Vec<Int>)::from(&[1i,2i,3i,4i] as Slice<Int>);
    let p: &Int = vec.index(1); // 后续增加运算符重载功能，可以写做 &vec[1]
    vec.push(5); // 此处可能导致 vec 扩容
    println(*p); // 如何保证 p 是合法的？
}
```

在这里，我们的策略依然是，在创建借用 `p: &Int` 的时候，增加底层数组的引用计数，在 `p` 死亡的时候减少引用计数。

问题是：如果 `p` 是一个借用，编译器怎么知道这个借用变量在死亡的时候要做引用计数操作，去哪个地址做引用计数操作？

答：上面这段代码能够编译，要靠编译器和标准库的一起配合才行。这里的取借用操作 `vec.index(1)` 实际上返回的不是一个原生借用类型 `&Int`，而是一个携带了额外数据的结构体，它是一个 “类似借用类型的智能指针类型”。
然后通过这个临时变量，再做 `deref` 操作，才获得最终的 `p: &Int` 借用指针。

```rust
// 该类型实现了 Deref trait，可以通过编译器插入的自动解引用得到 &T 类型；然后通过 &T 类型访问元素。
// 该类型实现了 Drop trait，可以在析构的时候减少对应数组的引用计数
struct ItemRef<'a, T> {
    ptr: *Shared<T>, // 指向数组头部
    item: &'a T, // 真正的借用
}
```

上述代码在编译器解糖之后，实际上是这样的意思：

```rust
fn main() {
    let mut vec = (type Vec<Int>)::from(&[1i,2i,3i,4i] as Slice<Int>);
    let _temp: ItemRef<Int> = vec.index(1); // 编译器隐式添加的局部变量，这是一个 “胖借用指针”
    let p: &Int = _temp.deref(); // 编译器隐式添加的 “自动解引用” 操作
    // 注意：如果我们没有 index 的返回值绑定到局部变量上，这个 _temp 应该在 index 语句结束后马上析构，而不是在语句块结束后析构。

    vec.push(5); // 扩容的时候，触发 copy-on-write 条件，分配新的空间，但旧的空间引用计数大于0，不释放，p 依然合法
    println(*p);
    // 编译器隐式析构 _temp 变量，此时导致旧的空间引用计数等于0，释放原数组中的内容
}
```

注：“自动解引用” 的规则是，在模式匹配、传参、返回场景下，如果存在 `T: Deref<U>` 则 `T` 可以通过自动调用 `deref` 成员函数转换为 `U` 类型。

为了能达到上述目标，zinc 标准库中的 Index trait 是这么定义的：
```
pub trait Index<Idx>
{
    type Output<'a>;

    fn index<'s>(&'s self, index: Idx) -> Self::Output<'s>;
}
```

注意 index 函数的返回类型不再是写死的原生借用类型 `&Item`，而是将 `&Item` 和其它数据一起封装起来的结构体类型 `struct ItemRef<'a, Item>` 。
我们可以把它视为自定义智能指针类型，是 “让原生借用类型携带了额外元数据” 的类型，可以看做是一种 “胖借用指针”。
因此这个 `Output` 关联类型，也必须定义为一种类型构造器，即 Rust 中的 generic associated type。
这个指针中不仅包含对具体元素的借用，还包含对内部数组头部的指针，且这个胖指针具有析构函数，它有足够的信息在运行时正确维护引用计数的值。

单从语义分析的角度来看，这么做貌似对性能影响很大。但是我们如果考虑把这里面用到的 `index` `deref` `drop` 几个关键函数都内联，是完全可以在性能优化阶段删除掉额外的引用计数操作的：
1. 如果在 main 函数中，没有调用过 push 等修改函数，没有对 vec 取过可变借用，那么编译器有充足的信息知道，这块内存没有释放风险，完全可以把所有的额外引用计数加减操作、和多余的局部变量全部删掉；
2. 如果在 main 函数中，存在对 vec 取可变借用并传递到其它函数中使用，编译器不确定 vec 是否可能被修改，此时保护性引用计数操作必不可少，这不算性能浪费。

## zinc如何解决经典的迭代器失效问题

在讲解 Rust 的内存安全特性时，以下是一个经典的例子：

```rust
///// Rust code
fn main() {
    let mut vec: Vec<i32> = Vec::from(&[1i,2i,3i]);
    for ref _i in &vec {
        vec.push(4);
    }
}
```

Rust 会对这个例子编译报错，因为 `vec.iter()` 创建了一个针对 `vec` 的只读借用，保存在迭代器里面；而 `vec.push` 需要创建一个针对 `vec` 的可读写借用。
根据 Rust 的借用检查规则，这两个之间会发生冲突，因此编译器报错，有效防止了迭代器失效问题，避免了 C++ 中常见的一种未定义行为。这是 Rust 值得表扬的优点。

Zinc 是用另外一种方式保证安全的。下面是 Zinc 的对应的代码，从源码层面看起来很像，但是实际执行效果，跟 Rust 有很大区别：

```rust
fn main() {
    let mut vec: Vec<Int> = (type Vec<Int>)::from(&[1i,2i,3i,4i] as Slice<Int>);
    for ref _i in vec {
        vec.push(4);
    }
}
```

1. 因为 zinc 里面没有 “所有权类型”，所以 `Vec<T>` 不是 move 语义，而是 copy 语义。我们可以随意 `let vec2 = vec;`，而且还能继续使用 `vec` 变量。
2. 虽然 `Vec<T>` 是 copy 语义，并不意味着它在执行拷贝的时候，就马上把所有的成员都拷贝一份，而是实现了 copy-on-write 优化。
在对 `Vec<T>` 拷贝的时候，只是浅拷贝，只是对内部堆上分配的数组的引用计数加 1，元素内容没有真的拷贝。
3. 深拷贝发生在对 `Vec<T>` 变量的修改的时候，如果在修改的时候，发现内部的数组的引用计数大于 1，那么就会把所有元素拷贝一份，然后再做修改。
4. 在上例中，创建迭代器的时候，会对内部的数组的引用计数加 1。如果在迭代的过程中，没有对 `vec` 的写操作，那么深拷贝就永远不会发生；
如果在迭代过程中，发生了 `vec.push`，这时候就会发现，此时需要触发深拷贝，`vec` 内部创建了一个新的数组，并在末尾加了一个 4。
5. 但迭代器指向的数组，并没有发生变化，没有释放也没有修改，迭代会继续执行。迭代器和 `vec` 已经是指向了完全不同的两个数组，因此是没有任何未定义行为的。
6. 等 for 循环执行完毕之后，迭代器的生命周期结束，它在析构的时候会将原数组的引用计数减 1，此时才会触发原数组的析构和释放。

所以说，zinc 同样避免了 “未定义行为”，没有引入 “内存不安全”，但是付出了一定的性能代价，在执行 push 操作的时候原 `Vec<T>` 类型隐式地做了一次深拷贝。
这个代价是可以接受的，我们既不想像 C++ 一样有未定义行为，也不想像 Rust 一样有过于严格的编译时检查，在保证 “安全” 和 “易用” 的前提下，执行性能损失已经是需要付出的最小的代价了。
如果用户希望节约这个深拷贝，那么就需要自己注意不要在循环过程中对原 vec 做修改。

对 Rust 来说，内存安全和线程安全是 **设计目标**。“可变和共享互斥原则” (alias XOR mutation principle) 是通向目标的 **理论基础**。
所有权(ownership)和借用检查器(borrow checker)是 **实现手段**。Zinc 选择了使用写时复制(copy-on-write)技术来实现同样的目标，殊途同归。
或者换一个角度说，Zinc 的这个设计是把编译阶段的 “可变和共享互斥” (alias XOR mutation) 静态检查改成了运行阶段保证。
copy-on-write 本质上就是保证在修改内存时候这块内存只有一个 alias，跟 ownership + borrow checker 异曲同工。详细对比如下：

* Rust 的编译时 ownership + borrow checker 检查，是在编译时保证，对象只有唯一的 mutable alias。但可以同时存在多个 immutable alias。

  如果违反 alias XOR mutation 原则，就编译报错。

* Rust 的 `RefCell<T>` 通过 `borrow` `borrow_mut` 成员函数使用。它是在运行时保证，对象只有唯一的 mutable alias，但可以同时存在多个 immutable alias。

  如果违反 alias XOR mutation 原则，就在运行时 panic，拒绝继续执行。

* Rust 的 `RwLock<T>`，通过 `read` `write` 成员函数使用。它是在运行时保证，对象只有唯一的 mutable alias，但可以同时存在多个 immutable alias。

  如果违反 alias XOR mutation 原则，就在运行时阻塞等待当前线程，直到满足条件之后继续执行。`Mutex<T>`是类似的，它保证了一块数据只能同时有一个访问者，不论读写。

* Zinc 的 copy-on-write，实现方式是，在 immutable method 里面不做 ref-count 检查；在 mutable method 里面做 ref-count 检查，保证在修改的时候对象只有唯一的 alias。

  如果违反 alias XOR mutation 原则，则把这个堆上分配的对象拷贝一份。保证了在修改内存/释放内存时只有一个 alias。

上述所有实现技术，都能满足同样的 "alias XOR mutation" 原则，它们都能达到 “内存安全” 的目标。Rust 的设计，只是实现 “内存安全” 的其中一种选择方案，绝对不是唯一可行的设计方案。

## 生命周期

所谓生命周期，就是指一个变量在程序执行过程中，在哪段区间内是活的。一个变量的生命周期在它创建的时候开始，在它销毁的时候结束。

### 全局变量的生命周期

全局变量，在整个程序的执行过程中都存活，所以它的生命周期是从程序开始到程序结束一直存在。

### 临时变量的生命周期

临时变量，指的是由表达式生成，但没有绑定到一个具体名字上的变量。

临时变量的生命周期结束的时机有两种情况：一种是在当前语句结束的时候结束；一种是在当前语句块结束的时候结束。这取决于它有没有被一个较长生命周期的变量借用。

示例如下：
```rust
fn f() -> S { ... }
// 假设 S 存在成员方法 method
impl S {
  fn method(&self) -> &S { return self; }
}

fn test() {
  f(); // f() 返回的这个变量，就是临时变量，它没有绑定到一个变量名上。这个临时变量在语句结束的时候生命周期结束。

  let p1: &S = &f(); // f() 返回的临时变量，被借用了，而且借用的生命周期超过了这条语句。那么这个临时变量的生命周期被扩展到了语句块结束的位置，在函数结束的时候，临时变量才会销毁。

  let p2: &S = f().method(); // f() 返回的临时变量，被借用了，而且借用的生命周期超过了这条语句。那么这个临时变量的生命周期被扩展到了语句块结束的位置，在函数结束的时候，临时变量才会销毁。
  // 使用 p1 p2
}
```

### 局部变量的生命周期

一般情况，局部变量，包括函数参数，的生命周期，是从它创建的时候开始，到当前代码块结束的时候结束。

没有 non-lexical-lifetime 这种东西，没有必要。Rust 引入这个东西，是因为 mut borrow 类型的独占性，如果分析不够精确会导致很多不必要的编译错误，限制用户的表达能力。如果我们没有编译时检查 mut borrow 的独占性这种规则，那也就不需要想办法放宽编译检查规则了。

* 对于自定义类型，我们可以给它实现 `Drop trait`，这种类型的变量，在生命周期结束的时候，会自动调用对应的析构函数。
* 对于 ARC 类型，在生命周期结束的时候，会自动将所指向的堆内存空间的引用计数减 1。
* 对于借用类型，它的析构函数不会做任何事情。

示例如下：
```rust
struct S { m: i32 }
impl Drop for S {
  fn drop(&mut self) {
    println("drop S");
  }
}

fn test() {
  let s1 = { .m = 1 }:S;
  let s2 = s1; // 此处发生拷贝

  // s1 和 s2 在 test 结束的时候析构
}
```

前面之所以说，“一般情况，是在代码块结束的时候，局部变量的生命周期结束”。就是说我们还有 “特殊情况”。特殊情况就是 `move` 表达式。

zinc 语言里面，move 关键字后面可以跟随一个表达式，称为 move 表达式。此时发生移动语义，而不是拷贝语义。

```rust
fn test() {
  let x = { .m = 1 }:S;
  let y = move x;
  println(x.m); // 编译错误，x 的生命周期已经结束，后面不能再使用 x
}
```

如果 move 的是 ARC 指针，我们可以利用这个功能减少一些场景下的引用计数增减操作：
```rust
fn f(arg: *S) { }

fn test() {
  let s: *S = box { .m = 1 }:S;
  f(s); // 如果这样调用，传参的时候发生拷贝，引用计数加 1，在 f 函数体末尾引用计数减 1。在退出 test 函数的时候引用计数再减1，
  f(move s); // 如果这样调用，可以确保，传参的时候引用计数不会自动加 1，也不会在 test 函数体末尾引用计数减 1。s 的生命周期转移给 f 的函数体维护。
  // s 被move之后，再使用 s 会触发编译错误

  // ...
}
```

如果我们希望让变量 `x` 提前结束生命周期，可以使用 `move x;` 语句，让 move 表达式的结果不要绑定到任何变量上，这个 x 就会在当场析构，而不是等到语句块结尾的时候析构。

总之，zinc 的 move 语义，选择权不在 “类型定义” 上，所有类型天然都是可以拷贝或者移动的。
是否使用 move 语义，选择权在 “表达式”。zinc 提供 move 语义的 “表达式” 而不是 move 语义的 “类型”。

`return` 语句默认是 move 语义，`return expr;` 等价于 `return move expr;`，不需要显式写 `move` 关键字。

## 析构函数 和 `Drop`

析构函数是对象的成员函数。在对象的生命周期结束的时候，由编译器自动插入指令调用析构函数。

析构函数做这样几件事情：
1. 调用该类型实现的 `Drop::drop` 函数，如果没有就不调用
2. 调用成员变量的 `Drop::drop` 函数
3. 将该类型包含的所有 Arc指针 和 Weak指针 类型的成员变量，对应的引用计数减 1。如果一个 ARC指针 指向的对象，引用计数降到了0，则自动调用该对象的析构函数。

析构函数永远是由编译器自动生成的，用户只能控制 `Drop::drop` 函数的行为，它只是析构过程中的一部分。
如果一个类型及其所有成员，都没有 `Drop::drop` 函数，以及引用计数类型的指针，那么这个类型的析构函数为空。

一般来说，用户不应该主动调用对象的析构函数。但在写 unsafe 代码的时候，允许用户通过 `unsafe fn destruct_in_place` 函数强制调用一个对象的析构函数。

`Drop::drop` 函数永远不能由用户显式调用。

用户自定义类型 `impl std::mem::Drop` trait 的示例如下：

```rust
struct S {
  p: *i32,
  m: String,
}

impl Drop for S {
  fn drop(&mut self) {
    println("S is dropped.")
  }
}
```

注意：自定义 `Drop::drop` 函数，不需要管成员变量的析构和内存释放，成员变量的析构函数会被自动调用。
