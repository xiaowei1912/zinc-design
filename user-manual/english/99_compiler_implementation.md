

## The zno file format

When the compiler compiles a library component, besides generating the corresponding `.o` binary file, it also needs to generate a C-style "header file" containing the signatures of all public interfaces for downstream libraries to use.
The "header file" generated by Zinc uses `.zno` as its file extension, meaning "zinc oxide."

The contents of a `.zno` file include all public function signatures, type definitions, global-variable declarations, impl declarations, and so on. They also include the bodies of all functions that can be inlined across components.

A `.zno` file format can in principle be plain text, or any custom binary format. But to speed up compilation, sqlite files were ultimately chosen. The reasons are explained below.

Consider this scenario: a large project contains many complex components. Component a depends on component b, and b in turn depends on other components c, d, e, and so on.
If a simple text-file format is used, then when compiling component a you would need not only to read in all of component b's zno file, but also to read in the zno files of all other components that b depends on, and then do syntactic and semantic analysis.
That is how C/C++ compilers implement `#include`.
But for Zinc's module system, it is not appropriate to copy C/C++'s design directly. Because C/C++ uses a file as the compilation unit, while Zinc uses a component as the compilation unit, and the compilation unit is larger.
By analogy, it would be like merging all of the headers used directly or indirectly by a fairly large C/C++ module into one huge file, and having every other file include this huge header at all times, rather than manually splitting it into several small headers.
We also have to consider the need for cross-component inlining; some function bodies also need to be recorded in this header file.
For large projects, an oversized header file is a large waste of compile time, because most of the contents of this pile of zno files are unused when compiling component a.
So can we consider letting zno support on-demand reading, reading only what is needed when compiling a? Split the zno file at the granularity of each "declaration," rather than reading the whole file as a unit.
For example, if component a simply uses one function `fn f();` from component b, then I know that the other function declarations, type definitions, and so on in b have nothing to do with component a, and b's dependents also have nothing to do with a.
I can pick that one function signature out of the `b.zno` file and do syntactic and semantic analysis, and ignore the rest. No matter how huge b's zno file is, or how complex its dependency tree is, that has nothing to do with compiling a.

To achieve the above, I need to split the entire header file into multiple parts by different declarations, and build an index for convenient queries, which is exactly what sqlite can help with.

Benefits of using the sqlite format:
1. sqlite is the most convenient format for supporting "on-demand reading." If we designed our own file format to achieve the same effect, we would likely end up with a more simplified, harder-to-use, buggier sqlite-format file.
2. Read/write speed is fast, and file size is appropriate. There are existing auxiliary tools, mature and stable, convenient for debugging. Later schema changes to extend functionality are also convenient.
3. At the current stage, for simplicity of implementation, serialized source is stored directly in sqlite; later this can be changed to store intermediate IR, further improving compile speed. That does not require changing the overall design.

A zno file does not need to care about human readability, because this file is for the compiler, not for people to read.
The function of being readable by people should be in a documentation-generation tool; we should provide a doc generator that produces attractive HTML documentation, with elegant layout, syntax highlighting, hyperlinks, search, and so on, convenient for humans to read.

## Bootstrapping

The first version of the Zinc compiler was implemented in C++; later the frontend was reimplemented in Zinc (of course not including the LLVM framework used by the backend). This was done for several purposes:

1. There is a famous saying in programming: "Eating your own dog food." Designers should first love the product they designed, and use their own product heavily over a long period; that effectively forms a Plan-Do-Check-Act loop and helps find problems early and improve them. I very much want my day-to-day programming language to be Zinc; using it directly to write its own compiler can accumulate first-hand usage experience as quickly as possible, and find and improve problems quickly. That the first version was not implemented in Rust is also related to this, because Rust's thinking habits and design patterns are quite different from Zinc. For example, many data structures inside a Rust-implemented compiler would have to use indices instead of pointers, a way of thinking quite different from other languages. Since it was already decided that it would later be rewritten in Zinc, it was better to write the first version in C++, so that the second version could migrate seamlessly without changing the main architecture.
2. After going open source, it is more convenient to accept contributions from other developers. If the compiler itself is implemented in C++, then when facing PRs from open-source contributors I do not know, I personally feel it is hard to review the code well and maintain code quality. Reviewing features implemented in a safe programming language is much simpler.
3. Practice the compiler-as-a-service idea. As everyone knows, a programming language is not just implementing a compiler; it also needs a whole ecosystem to be truly useful. The toolchain part of that ecosystem includes IDE support, an auto-formatter, a package manager, a documentation generator, custom lint warnings, code-quality analysis, and a series of other tools. Many parts of these tools need to share the same logic with the compiler. So if we can make each part of the compiler itself a conveniently callable library, with a safe, easy-to-use API, then building surrounding tools is twice the result for half the effort. Conversely, if the compiler is a black box whose components cannot be easily reused, then building surrounding tools involves a large amount of duplicated work, half the result for twice the effort. Using C++ as the public API of the compiler's own subcomponents is not safe or easy enough.
4. Lay a foundation for later metaprogramming (macros, custom lints, and so on). Metaprogramming, from an implementation perspective, is really a compiler-plugin feature. The compiler needs to dynamically load some modules and execute those plugins during compilation. Of course we want macro definitions themselves to be implemented in Zinc. And Zinc happens to be a language relatively well suited to being compiled into dynamic libraries, and the APIs of those compiled libraries can also support advanced features such as generics and traits. If the compiler, as the caller, is also implemented in Zinc, then this plugin mechanism is very clean and simple. Conversely, if C++ dynamically loads a Zinc dynamic library, it can be done, but it is clearly extra trouble.

## Brief overview of the compiler structure

The compiler is split into these components:
* zinc_cli, an executable that depends on the following components. Internally it mainly contains command-line handling.
    * options
    * session
* zinc_frontend, the compiler frontend, responsible for syntactic and semantic checking. It contains several submodules, of which the two most important are:
    * zinc_syntax  The main input is source, and the output is the SyntaxTree data structure. Includes syntax-error reporting. The lexer is also included in this component.
    * zinc_semantic  The main input is the SyntaxTree data structure, and the output is the SemanticModel data structure. Includes semantic-error reporting.
        * hir
        * mir
* zinc_backend, the compiler backend, responsible for performance optimization and code generation. It contains several submodules, of which the two most important are:
    * optimization  Performance optimization; the input is the SemanticModel data structure, which it modifies and transforms
    * llvm_ir_gen  The main input is the SemanticModel data structure, and the output is LLVM IR. It also contains some performance optimizations.


They all depend on zinc_std, which is Zinc's standard library.

## No function overloading based on parameter types

The main purpose is to better support publishing components via dynamic libraries.

The core scenario is: when a component is published as a dynamic library, we expect that when the library version is later updated, downstream users do not need to recompile their code and can link and use it directly.

Now suppose we support function overloading based on parameter types, and consider this situation:
lib_v1 has a function whose signature is `fn f(arg: *Base);`; in the lib_v2 version we want to add an overloaded version `fn f(arg: *Sub);`, where `Sub` is a trait that inherits from `Base`.
If downstream users do not recompile their code, when used together with lib_v2 the code can still execute, but it will always call the `Base` version. The newly added overload will never take effect.

When we say "function overloading based on parameter types is not supported," what we actually mean is "function-version resolution based on parameter types at compile time is not supported"; we force the user to do function-version resolution at runtime.

Still in the scenario above, if the user needs extra handling of a `*Sub` argument in lib_v2, the user needs to modify the original function's body, rather than adding an overloaded function signature:
```
fn f(arg: *Base) {
    if (arg is s:*Sub) {
        // judge via pattern matching; if arg is *Sub, execute special logic
    } else {

    }
}
```
After the new version lib_v2 dynamic library is published, the executable does not need to be recompiled, and the application's behavior is updated automatically.

This of course sacrifices execution efficiency. But to achieve seamless updates of dynamic libraries, this runtime cost must be paid. Compile-time overload resolution cannot obtain this kind of dynamism.

This design has no expressiveness problem, only an execution-performance problem. And execution performance has a chance to be partly recovered through various optimizations. Especially when the user does not need "publishing an ABI-stable dynamic library," they can tell the compiler via a compile option to enable more aggressive optimizations.

## No exceptions, no stack unwind

Zinc provides the `panic` keyword, which can be compared to the `throw` keyword in other languages. But it is not the same thing as `throw` in other languages or `panic!` in Rust.

Rust's panic has two behavior modes, `abort` and `unwind`, which can be specified via the following `rustc` compile option.
```
-C    panic=val -- panic strategy to compile crate with
```
* Rust's `panic` under the `abort` strategy terminates the process immediately; the `catch_unwind` function has no effect. It is equivalent to calling libc's `abort` function.
* Rust's `panic` under the `unwind` strategy performs stack unwind, and calls the destructors of local variables in each layer of the function, including automatically decrementing ARC pointer reference counts, and it can be caught by `catch_unwind`, which stops the unwind. This process is similar to exceptions in other languages.

Zinc's `panic` simply prints the call stack and then aborts. It has no unwind process and cannot be caught; it is equivalent only to Rust's `panic` under the `abort` strategy. Zinc does not support `unwind` behavior.

This design was inspired by nikomatsakis's [blog post](https://smallcultfollowing.com/babysteps/blog/2024/05/02/unwind-considered-harmful/), and was chosen for the following reasons:

1. unwind increases the implementation difficulty of the compiler and standard library
    1. unwind increases code size. Because every function call may unwind, the compiler needs to record, at every place that may unwind, which local-variable destructors to call.
    2. unwind reduces optimization opportunities. The control-flow graph becomes more complex; many places gain an extra control-flow edge that may unwind, which affects the compiler's static analysis.
    3. unwind requires the standard library, when implemented, to consider exception safety.
2. unwind increases the user's learning and usage cost
    1. As a latecomer language, Zinc will find it hard to build an independent ecosystem. In most applications, people will likely only use Zinc to develop one of the modules, which means interop is important. If Zinc introduces an unwind mechanism, what is its relationship with existing C++ exceptions and Rust panics? Can they catch each other? If we want a low-level module written in Zinc to be callable by higher-level languages such as Go/C#/Java/Javascript/Python, can those high-level languages catch a panic thrown by Zinc? Is this mechanism convenient for users, or does it add chaos?
    2. Introducing an unwind mechanism into the language requires every third-party library, when designed, to consider exception safety. Especially when unsafe and interop are involved, this is hard. Zinc's positioning emphasizes simplicity and ease of use; is requiring ordinary developers to also consider exception-safety design asking a bit much?
    3. Which error-handling scenarios are inconvenient to express with `Option` `Result` and must use a catchable unwind? If we implement this feature, which scenarios would benefit, and are those scenarios persuasive enough?

I believe Zinc's ecosystem should be built like this: all "recoverable errors" uniformly return `Option/Result` types; this kind of error means the current process has a way to handle it when it is encountered. All "unrecoverable errors" uniformly use `panic`; this kind of error means the current application has no way to handle it at runtime; it is a bug in the code, and the only solution is to go back, modify the code, recompile the program, and run it again.

If someone disagrees with this decision, they need to write a complete design proposal to open a discussion, and the contents should fully answer the questions above.
